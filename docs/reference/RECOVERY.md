# Recovery contracts

## Separate recovery scopes

| Scope | Boundary |
| --- | --- |
| Normal TTY administration | User's normal login and fresh sudo credential, for diagnosis and controlled file/release repair |
| Optional Senomy Recovery | Separately authenticated restricted password-reset convenience; not an alternate desktop |
| Source publication rollback | Exact stage preimages, modes and postimage-drift refusal |
| Component deployment rollback | The owned transaction receipt, separate from unrelated files and live processes |
| Versioned-release recovery | The exact verified release journal/bindings, distinct from user-data or running-process restoration |
| Boot/media recovery | Requires its own supported boot path and acceptance |

Normal-account TTY access cannot replace credential-loss recovery if the normal
password is forgotten. The optional graphical password-reset session is not a
release-engine dependency. Do not claim broad recovery acceptance from a checksum or isolated fixture.

## Restricted password-reset path

The SDDM Recover route authenticates the separate recovery account, then uses its
root-owned session launcher, minimal Hyprland, GTK recovery UI and exact confined
password-reset helper. It does not run a general application launcher or arbitrary user checkout. It depends on working graphics/
SDDM/Hyprland and is not universal rescue media. Never put credentials/shadow data
into project evidence.

Preserve session guards, recovery confinement, root ownership/modes and exact target
validation. Normal login selection excludes the recovery session. A future explicit
retirement must lock/verify the account before removing confinement; hiding a
button alone does not retire it. Preserve recovery state/preimages and do not
remove shared SDDM/Hyprland/Python/GTK/sudo packages. Update bootstrap, manifests,
greeter and guarded launch paths together only within an authorized transaction.
Account/group/home deletion is a separate decision.

Sources are under `components/recovery/`, `scripts/senomy-recoveryctl`, system
manifests and SDDM integration. Current acceptance is in [PROJECT_STATE](../PROJECT_STATE.md).

## Runtime repair and preimages

Diagnose first with `scripts/senomy-shell status`/`doctor`. A shell restart removes
Rails/panels briefly and ends the telemetry epoch; the application-lifetime guard
must remain. Preserve independent ordinary-app ownership and installed-root
validation. Never bypass a refusing guard to obtain a successful test.

Restore only a reviewed stage after checking no later source changes would be
overwritten. Source restoration may trigger QML watching; announce it as runtime
publication. Private publication snapshots and frozen QA patch preimages remain
recovery evidence. Restoring source does not revert an active hardware preview;
use its owned Keep/Revert/recovery transaction. Do not remove recovery accounts,
receipts, user data, drafts as routine document cleanup.
